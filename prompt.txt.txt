Here are the strict structural and architectural specifications you must follow:

### 1. Database Schema Setup (PostgreSQL 17)
Create database migration scripts or initialization files supporting the following schemas. Every single table must contain standard audit tracking fields:
- `created_at` (TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP)
- `updated_at` (TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP)
- `created_by` (VARCHAR/INT, indicating system, user ID, or 'anonymous_signup')
- `updated_by` (VARCHAR/INT)

Tables to create:
- `users`: id, email (unique, indexed), password_hash (nullable for Google Auth), name, avatar_url, provider (ENUM: 'LOCAL', 'GOOGLE'), google_id (unique, indexed), status (ENUM: 'ACTIVE', 'INACTIVE', 'DEACTIVATED').

### 2. Standardized Global API Response Interface
You must implement a unified JSON response envelope pattern. Every single controller and error middleware must return data matching this exact runtime layout:

For Success (HTTP 200/201):
{
  "success": true,
  "status": 200,
  "message": "Operation completed successfully.",
  "data": { ... }, 
  "error": null
}

For Errors (HTTP 4xx/5xx):
{
  "success": false,
  "status": 400,
  "message": "Clear, user-friendly descriptive error text for UI toast messages.",
  "data": null,
  "error": {
    "code": "INVALID_CREDENTIALS",
    "details": "Specific validation array or non-sensitive debug context if in development environment"
  }
}

### 3. Core API Endpoints to Implement
- POST `/api/auth/signup`: Registers local user. Enforce secure password hashing using bcrypt. Check for existing emails defensively.
- POST `/api/auth/login`: Validates local users. Generates a secure, signed JWT.
- POST `/api/auth/google`: Handles Google OAuth tokens. Use an Upsert (Idempotent) strategy: if user doesn't exist, create them as ACTIVE; if they do exist, log them in.
- POST `/api/auth/google/delink`: Changes user status to 'INACTIVE', clears `google_id`, but preserves their historical record. 
- DELETE `/api/users/delete`: Hard deletes or completely anonymizes the user account in compliance with GDPR.
- GET `/api/users/profile`: Protected route returning current user's profile details.

### 4. Enterprise Security & Edge-Case Requirements
- Global Error Handler Middleware: Catch ALL unhandled promises, syntax errors, and database connection exceptions. Map them cleanly to the standardized error response layout with HTTP 500 status, ensuring no raw system stack traces are exposed to the client.
- Brute-Force Protection Middleware: Integrate Redis. If an IP or email triggers 5 failed login attempts within 15 minutes, block them immediately at the middleware layer before querying PostgreSQL, returning an explicit 'TOO_MANY_REQUESTS' error code.
- Input Validation: Implement strict schema validation (using a library or robust manual checks) on incoming bodies for missing fields, malformed emails, and weak passwords before hitting database routes.
