# Project Context: Nearby Locator

This document serves as the authoritative source of truth for the **Nearby Locator** application. It has been generated by thoroughly analyzing the entire repository (frontend, backend, database, infrastructure, and configuration files).

## 1. Executive Summary
Nearby Locator is a location-aware web application that enables users to discover points of interest (restaurants, hospitals, pharmacies, etc.) near their coordinates using natural language conversational search. The system features a modern React-based frontend and a robust, layered Express/Node.js backend with PostgreSQL and Redis.

## 2. Project Goals
- Provide a conversational search engine capable of fuzzy NLP parsing.
- Implement secure user profile management, including local credentials and Google OAuth.
- Maintain a premium, micro-interactive UI utilizing TailwindCSS and glassmorphism principles.
- Offer telemetric analytics and robust brute-force security controls.
- Maintain a scalable, layered backend architecture capable of background job processing.

## 6. High-Level Architecture
The system follows a decoupled Client-Server architecture. The React SPA (Frontend) communicates with the Node.js/Express API Gateway (Backend) over a stateless JSON REST API. 
The backend connects to a PostgreSQL database for persistent storage (users, roles, spots, logs) and a Redis cache for volatile data (rate limits, brute-force tracking, session telemetry). The backend also proxies requests to the Google Places API for location discovery.

## 7. Detailed Backend Architecture
The backend strictly adheres to a **Layered Architecture (N-Tier)**:
1. **Routes (`/routes`)**: Define API endpoints and attach middleware.
2. **Controllers (`/controllers`)**: Handle HTTP request extraction, response formatting, and delegate to services.
3. **Services (`/services`)**: Contain pure business logic (e.g., `authenticationService`, `rbacService`, `spotService`).
4. **Repositories (`/repositories`)**: Encapsulate all direct database queries using Knex, abstracting SQL from the business logic.

**Additional Subsystems:**
- **Background Jobs (`/jobs`, `/utils/queue.js`)**: A custom worker system that processes async tasks (e.g., analytics rollup, notifications).
- **Observability**: Prometheus metrics exposed at `/metrics`, structured logging via Pino, and database query telemetry.

## 8. Detailed Frontend Architecture
The frontend is a React SPA structured around feature isolation and lazy loading.
- **Routing**: Handled by `react-router-dom` `createBrowserRouter`. Pages are lazy-loaded via `Suspense` for code splitting. Protected routes and Admin routes are enforced via layout wrappers.
- **State Management**: Global UI/Auth state is managed by Zustand (`store/useAuthStore.js`). Remote server state (API caching) is managed by React Query.
- **Styling**: TailwindCSS is the primary styling engine, focused on utility classes.

## 9. Database Architecture
PostgreSQL schemas are managed via Knex migrations. Key modules include:
- **Identity:** `users`, `user_oauth_accounts`, `user_sessions`, `auth_tokens`, `login_history`, `login_attempts`.
- **RBAC:** Roles and permissions tables (introduced in `20260710_create_rbac_architecture.js`).
- **Core Data:** Spatial data/spots, analytics, system errors, notifications.
The database uses UUIDs (`gen_random_uuid()`) for primary keys and enforces strict relational integrity.

## 10. Authentication Architecture
- **Stateless Bearer JWT:** Standard authentication uses JWTs.
- **Local Strategy:** Email and bcrypt-hashed passwords.
- **OAuth Strategy:** Google Identity Services integration.
- **Session Tracking:** `user_sessions` table and Redis are used to track and optionally revoke active sessions.
- **Flows:** Signup, Login, Email Verification, Forgot Password, Reset Password are fully implemented on both frontend (pages) and backend (services/controllers).

## 11. Authorization Model
A Role-Based Access Control (RBAC) system restricts endpoints based on user roles and granular permissions.
- Implemented via `requirePermission(permission)` middleware.
- Cached in Redis (`rbacCache.js`) to minimize DB lookups.
- Standard roles include `user` and `admin`.

## 12. Security Architecture
- **Brute-Force Protection:** Redis-backed sliding window rate limiter intercepts failed login attempts and blocks IPs/Emails temporarily.
- **CORS:** Strictly configured allowed origins.
- **Error Handling:** Global `errorHandler` middleware catches uncaught exceptions, logs stacks securely to `system_errors` DB table, and prevents leaking stack traces to the client.

## 13. API Architecture
APIs are JSON REST endpoints mounted under `/api/*`, returning standardized payloads via `responseFormatter` middleware:
```json
{
  "success": true,
  "status": 200,
  "message": "...",
  "data": {},
  "error": null
}
```
OpenAPI specification is generated via Redocly and served on `/api-docs/v1`.

## 14. State Management
- **Frontend Local State:** React `useState`.
- **Frontend Global State:** Zustand (`useAuthStore` for session, `useUIStore` for interface toggles, `useToastStore` for notifications).
- **Frontend Server State:** @tanstack/react-query (for data fetching and caching).

## 15. Infrastructure
- **Dockerized:** `docker-compose.yml` spins up `backend` (Node), `frontend` (Nginx), and custom networks.
- Local development utilizes `docker-compose.dev.yml` for hot-reloading with host volume mounts.
- PostgreSQL and Redis are expected as external services or local containers.

## 16. Build & Deployment
- Frontend uses `npm run build` (vite) to generate static files in `dist`, which are served by Nginx in production (`Dockerfile`).
- Backend runs directly via `node index.js` after executing Knex migrations (`npm run migrate`).

## 17. Environment Configuration
Strict environment validation occurs at boot.
- Frontend: `src/app/config.js` uses Zod/assertions to validate variables like `VITE_BACKEND_URL`.
- Backend: `config/index.js` uses Joi to validate `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, etc. The server will crash on boot if configuration is invalid.

## 20. Coding Standards
- **ES Modules:** Explicit use of `import`/`export` across the entire codebase.
- **Async/Await:** Used exclusively for asynchronous operations. No raw Promise chains.
- **Layered Architecture:** Controllers must not write raw SQL; they must use Services, which use Repositories.
- **Early Exits:** Guard clauses are preferred over deeply nested `if` statements.

## 21. Project Conventions
- All primary database keys are `UUID`s.
- Custom React Hooks are grouped in `src/hooks`.
- API calls on the frontend must use the `services/api.js` Axios singleton to ensure interceptors (JWT injection, 401 handling) trigger correctly.
- Background jobs are registered in `jobs/index.js` and extend a base job class.

## 22. Current Project Status
The core architecture is heavily developed, with extensive backend foundation (RBAC, Telemetry, Auth, Mailers). The frontend has a complete routing structure and state management scaffolding. The application is functional but has localized technical debt requiring cleanup.

## 23. Technical Debt
- **Missing Dependency:** `recharts` is imported in frontend but is missing from `frontend/package.json`.
- **In-Memory Lists:** The `/lists` API endpoints currently reside directly in `backend/index.js` and use an in-memory `Map()`. These will lose data on restart and bypass the layered architecture. They must be migrated to a PostgreSQL table (e.g., `saved_places`) and moved to a dedicated Controller/Service.
- **Monolithic Search:** The `POST /nearby` endpoint is directly embedded in `backend/index.js` instead of utilizing the `discoveryController.js`.
- **Static Telemetry Data:** `analyticsTracker.js` hardcodes geo-IP lookup (e.g., `const country = 'US'`).

## 24. Known Limitations
- Google Places API rate limits will strictly cap the application's throughput under high load.
- In-memory Lists (as noted in tech debt) prevent horizontal scaling of the backend.

## 25. Future Expansion Points
- **Refactoring:** Moving `/nearby` and `/lists` from `index.js` into their respective Controller/Service layers.
- **Geo-IP Integration:** Replacing static country assignments with a library like `geoip-lite`.
- **PWA Capabilities:** Enhancing the React application with a Service Worker for offline capabilities.
- **Real-time Notifications:** WebSockets for instant user alerts based on the existing Notification Jobs architecture.
